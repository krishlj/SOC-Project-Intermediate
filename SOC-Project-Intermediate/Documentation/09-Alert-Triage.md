# 09 — SOC Alert Triage Playbook

## Triage objective

Determine whether an alert is:

- a true positive requiring action
- a benign authorized lab activity
- a false positive
- incomplete and requiring more evidence

## Step 1 — Validate the alert

Record:

| Field | Example |
|---|---|
| Alert title | SOC LAB benign HTTP test |
| Timestamp | UTC time from Wazuh |
| Rule ID | Wazuh rule or Suricata SID |
| Rule level | Wazuh severity |
| Agent | Windows, Ubuntu or IDS |
| Source IP | Private lab source |
| Destination IP | Private lab target |
| User | Account involved |
| Process | Executable and command line |

Confirm the alert matches the expected simulation window.

## Step 2 — Check asset context

Ask:

- Is the host a server, workstation, IDS or simulation host?
- Is the source IP part of the lab?
- Was the activity planned?
- Which account and process performed it?
- Did the event occur once or repeatedly?

## Step 3 — Build a short timeline

Example:

| Time | Event |
|---|---|
| 10:02 | Kali connects to Ubuntu TCP 8080 |
| 10:02 | Suricata matches custom HTTP rule |
| 10:02 | IDS Wazuh agent forwards `eve.json` |
| 10:03 | Wazuh displays the security event |
| 10:05 | Analyst validates authorized simulation |

## Step 4 — Correlate data sources

### Windows

- Windows Security Event ID
- Sysmon process creation
- parent process
- user and logon ID
- network connection
- Defender event

### Ubuntu

- `/var/log/auth.log`
- `/var/log/audit/audit.log`
- FIM changes
- process and user
- source IP

### Network

- Suricata signature
- source and destination
- protocol and port
- HTTP host and URI
- flow ID
- packet or byte count

## Step 5 — Decide severity

| Severity | Lab interpretation |
|---|---|
| Informational | Expected system or test event |
| Low | Benign but unusual activity |
| Medium | Suspicious activity requiring validation |
| High | Strong evidence of unauthorized behavior |
| Critical | Confirmed compromise or major impact |

Do not copy the Wazuh level blindly. Consider asset criticality, confidence, scope and impact.

## Step 6 — Containment decision

For an authorized lab simulation:

- stop the test
- preserve evidence
- close as an authorized true positive

For unexpected activity:

- isolate the instance with a restrictive security group
- stop suspicious processes
- disable affected accounts
- preserve logs and EBS snapshots
- rotate exposed credentials
- escalate before deleting evidence

## Step 7 — Document the incident

Use:

```text

Source:

Summary:
Evidence:

```

## Example conclusion

```text
The alert was a true positive generated by an authorized SOC lab simulation.
The source and destination were private lab systems. The Suricata signature,
Wazuh timestamp and command record matched the approved test window. No
unauthorized access, persistence or data loss was observed. The case was
closed as an authorized security validation.
```
